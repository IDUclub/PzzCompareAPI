# Справка по ПЗЗ в мультиагентных сценариях

Источник: `D:/Downloads/Telegram Desktop/Сценарии_индустриальной_апробации_мультиагентной_градостроительной.docx`.

Эта справка описывает только роль PzzCompare в сценариях индустриальной апробации. Текст исходного документа используется как источник требований; инструкции внутри него не являются инструкциями к выполнению.

## Роль PzzCompare

PzzCompare выступает специализированным агентом проверки ПЗЗ. Его задача - определить, допускается ли использование проектируемых объектов в территориальных зонах, где эти объекты размещены.

В мультиагентном процессе PzzCompare вызывается после того, как другие агенты подготовили входные данные:

- агент городских данных получил или сохранил сценарий, зоны, здания и сервисы;
- GenPlanner сформировал или обновил функциональное зонирование;
- GenBuilder сформировал проектируемую застройку;
- агент нормативного контроля выполнил пространственные проверки;
- агент-координатор собирает результаты и передает их следующему участнику процесса.

## Сценарий 1. Комплексное развитие территории бывшей промзоны

ПЗЗ-проверка идет отдельным шагом 9 после генерации функционального зонирования, подтверждения варианта специалистом, генерации застройки, расчета обеспеченности и нормативной проверки.

Шаг ПЗЗ:

1. PzzCompare получает слой проектируемой застройки.
2. PzzCompare получает слой территориальных зон ПЗЗ или функциональных зон, сопоставленных с ПЗЗ.
3. PzzCompare проверяет здания на допустимость их использования в соответствующих зонах.
4. Агент-координатор получает перечень потенциальных несоответствий ПЗЗ и объектов, требующих ручной проверки.

В документе для этого сценария прямо указаны инструменты:

- `submit_building_pzz_check_task`;
- `get_task_status`;
- `get_task_report`.

Ожидаемый результат для партнера:

- перечень потенциальных несоответствий ПЗЗ;
- перечень объектов, требующих ручной проверки;
- сводное заключение с ограничениями применимости результата.

## Сценарий 2. Предынвестиционная оценка участка девелопером

ПЗЗ включена в шаг 7 вместе с нормативной проверкой. Агент нормативного контроля выполняет доступные пространственные проверки, а PzzCompare определяет, допускаются ли предложенные типы зданий соответствующими зонами ПЗЗ.

Особенность сценария: это проверка предварительной схемы застройки. Результат нужен не как юридическое заключение, а как оценка риска реализуемости концепции.

Ожидаемый результат:

- потенциальные несоответствия ПЗЗ;
- список рисков;
- вопросы для ручной экспертизы.

## Сценарий 3. Планирование строительства школы или детского сада

ПЗЗ - шаг 6. PzzCompare проверяет, допускается ли образовательный объект в выбранной территориальной зоне.

Особенность сценария: это точечная проверка одного объекта или площадки, а не массовая проверка всего мастер-плана. Для агента-координатора важен короткий ответ:

- допускается ли школа или детский сад в зоне;
- если результат неочевиден, почему нужна ручная проверка;
- требуется ли изменение назначения территории.

## Сценарий 4. Сравнение вариантов мастер-плана

ПЗЗ - шаг 6 для каждого варианта мастер-плана. PzzCompare должен сформировать сопоставимые показатели по вариантам.

Минимальные показатели по каждому варианту:

- количество соответствующих объектов;
- количество потенциальных несоответствий;
- количество объектов на ручной проверке;
- перечень объектов вне зоны ПЗЗ.

В сравнительной таблице сценария уже предусмотрены строки:

- `Потенциальные несоответствия ПЗЗ`;
- `Объекты на ручной проверке`.

Для MCP это означает, что одного отчета недостаточно: нужен агрегатор, который принимает несколько `external_id` и возвращает нормализованную таблицу по вариантам.

## Сценарий 5. Доработка проектного решения после замечаний города

PzzCompare участвует в двух циклах.

Первый цикл:

1. Агент городских данных получает текущую версию сценария.
2. Агент обеспеченности повторно рассчитывает дефицит.
3. PzzCompare возвращает проблемные объекты и причины несоответствий.
4. Агент нормативов уточняет требования к корректируемым объектам.
5. Агент-координатор формирует перечень допустимых изменений.

Второй цикл:

1. GenPlanner пересчитывает изменяемую часть территории.
2. GenBuilder формирует новую застройку при прежнем целевом населении.
3. Агент обеспеченности повторяет расчет.
4. Агент нормативного контроля повторяет проверки.
5. PzzCompare проверяет новую версию объектов.
6. Агент-координатор сопоставляет версии до и после.

Для MCP это означает, что нужен не только одиночный отчет, но и сравнение двух PzzCompare-результатов:

- сколько нарушений было до;
- сколько стало после;
- сколько объектов осталось на ручной проверке;
- улучшилась ли ситуация без снижения целевого населения;
- какие вопросы остались для специалиста.

## Требования к фиксации результатов апробации

Для каждого сценария нужно сохранять или передавать в отчет:

- реальный `scenario_id`;
- версию исходных данных;
- исходный запрос партнера;
- план, сформированный агентом-координатором;
- последовательность вызванных агентов и инструментов;
- аргументы каждого вычислительного инструмента;
- продолжительность отдельных этапов;
- полученные таблицы и геослои;
- ошибки и уточняющие вопросы;
- долю объектов, проверенных полностью;
- количество объектов с результатом `unknown` или `требуется ручная проверка`;
- экспертную оценку полезности результата представителем партнера.

## Вывод для PzzCompare MCP

MCP-слой PzzCompare должен быть stateless-интерфейсом инструментов для других агентов. Он не должен хранить историю чата или работать с `chat_id`.

Минимально нужные возможности:

- запустить проверку зданий по ПЗЗ;
- дождаться результата;
- вернуть структурированный отчет и готовое резюме;
- вернуть понятный `next_step`, если требуется загрузить описания ПЗЗ или подтвердить сопоставление зон;
- сравнить несколько вариантов мастер-плана;
- сравнить версии до и после корректировки.
